# 第三部分：工单管理闭环

参考目录：`03-tickets`。它是在第二部分上增加工单功能后的完整版本。

## 先明确做到哪里

客服可以在页面创建工单、分页查询、筛选、查看详情、修改信息、选择负责人、
填写处理记录、保存解决方案，并按顺序关闭工单。

```text
待处理 → 开始处理 → 处理中 → 填写解决方案 → 已解决 → 确认已回复客户 → 已关闭
```

当前“已回复客户”由客服人工确认。页面不会调用 SMTP，
也不会伪造发送记录；第七部分生成回复草稿，第十一部分再接 SMTP 邮件发送。

## 第二步：认识工单字段

| 字段 | 大白话解释 | 由谁填写 |
|---|---|---|
| id | 数据库内部编号 | 数据库生成 |
| number | 显示用的工单编号，如 T000001 | 后端根据 id 生成 |
| title | 一句话概括问题 | 客服 |
| description | 详细问题描述 | 客服 |
| customer_name | 提出问题的客户姓名 | 客服 |
| customer_email | 客户接收后续回复的邮箱 | 客服 |
| product_id | 发生问题的产品编号 | 从配置中选择 |
| module_id | 产品下的模块编号 | 从所选产品的模块中选择 |
| category_id | 问题分类编号 | 从配置中选择 |
| owner_id | 当前负责人编号 | 创建时取创建人，编辑时可分配 |
| priority | P1、P2、P3、P4 | 客服选择 |
| status | pending、processing、resolved、closed | 由对应业务动作推进 |
| solution | 解决问题的办法 | 标记已解决时填写 |
| created_at / updated_at | 创建和最后处理时间 | 后端/数据库记录 |

前端显示“待处理”，接口实际传 pending。这是本项目约定，显示文字可以改，
枚举代码则需要前端、后端、数据库约束一起调整。

## 第三步：认识接口

| 方法和路径 | 作用 | 需要注意 |
|---|---|---|
| POST /api/tickets | 创建工单 | 初始待处理，负责人为当前用户 |
| GET /api/tickets | 分页、关键词和多条件筛选 | page 从 1 开始，page_size 最大 100 |
| GET /api/tickets/{id} | 获取详情与处理记录 | 不存在返回 404 |
| PATCH /api/tickets/{id} | 修改提交的字段 | 不提交的字段保持原值；必填字段不能设 null |
| POST /api/tickets/{id}/records | 添加处理记录 | 内容不能为空 |
| POST /api/tickets/{id}/start | 开始处理 | 只允许从待处理进入处理中 |
| POST /api/tickets/{id}/resolve | 保存解决方案并解决 | 只允许从处理中进入已解决 |
| POST /api/tickets/{id}/close | 确认人工回复并关闭 | 只允许从已解决进入已关闭 |

状态变化使用单独接口，是因为“开始处理”“保存解决方案”“确认关闭”有不同业务要求。
通用编辑接口不能随意写 status，所以绕过按钮直接发 PATCH 也不能跳过流程。

## 第四步：读懂后端三个文件

### schemas.py：检查输入

`TicketCreate` 规定新工单必须提交哪些字段。
`TicketPatch` 区分“字段没提交”和“提交了 null”，否则可能误把必填内容清空。
`ResolveRequest` 要求有效解决方案。`CloseRequest` 要求明确确认客户回复。

标题最长 200、正文最长 10000，是项目设置的业务上限，不是 Python 固定限制。
要改时同步前端 maxlength、后端校验；涉及数据库列长度时还需要迁移。

### service.py：放被多个接口使用的业务操作

- get_ticket：读取工单，不存在时报告 404。
- lock_ticket：写操作先锁定这一张工单；已关闭则拒绝修改。
- validate_catalog：确认产品、模块、分类存在，模块属于产品，新的选择没有停用。
- validate_owner：新负责人必须是启用用户。
- add_record：更新处理时间，并准备一条带操作人的处理记录。

这些函数都有当前调用方，不是为假设的未来场景准备的通用框架。

### router.py：把一次操作串起来

例如标记已解决：

```text
核对登录用户
 → 校验提交的解决方案
 → 锁定工单
 → 确认工单当前为处理中
 → 保存解决方案
 → 状态改成已解决
 → 增加一条处理记录
 → 一次提交
 → 返回详情
```

保存工单和增加处理记录处于同一事务。
若提交失败，不会先返回成功或留下只有状态没有记录的半套修改。

同一工单的写入使用 PostgreSQL 行锁。两名客服同时点“开始处理”，只有一个请求能成功，
另一个看到工单已经进入处理中后得到 409。

## 第五步：读懂前端页面

- TicketsView：向接口提交筛选条件，再把返回的 items 放进表格。
- TicketEditor：新建和编辑共用一个表单；创建时用户主动选择优先级，不预填虚假的选择。
- 表单只有在所需配置、用户和原工单成功加载后才出现；加载失败只展示错误，避免填写并提交缺少原始数据的编辑表单。
- TicketDetailView：根据当前状态显示可用动作，展示实际解决方案和实际处理记录。
- api/tickets.ts：集中列出本阶段实际用到的工单请求。
- api/models.ts：校验工单响应格式，页面内部无需重复检查每一个字段。

表单初始空字符串表示尚未输入；null 表示尚未拿到详情；
空数组表示尚未加载到列表或结果为空。这些状态都配合 loading/error 展示，不表示请求默认成功。

## 第六步：手工走完一个例子

1. 管理员先创建“云办公”产品，再给它创建“账号管理”模块。
2. 选择预置的“账号权限”分类。
3. 创建工单“新账号无法登录工作台”，填写模拟客户邮箱，选择 P3。
4. 在列表按标题搜索，打开详情，确认信息正确。
5. 修改标题或负责人，保存后再次打开核对。
6. 点击“开始处理”，添加一条“已联系客户核对激活状态”的记录。
7. 填写“激活账号后重新登录成功”，点击保存并标记已解决。
8. 人工完成客户回复后，勾选确认，点击关闭。
9. 确认已关闭页面保留解决方案与记录，并且没有继续修改按钮。
10. 重启后端，重新登录，查看这张工单仍然存在。

使用 example.com 邮箱可以完成本阶段演示，不会真的发送邮件。

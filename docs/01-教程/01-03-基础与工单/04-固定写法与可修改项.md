# 固定写法与可修改项

“固定”不是把整段代码永久背下来，而是分清语法、库的 API、项目约定和本地参数。

## 第一类：语法和库的 API，按规定拼写

| 代码 | 大白话解释 | 注意 |
|---|---|---|
| import / from / def / return | Python 的导入、函数和返回语法 | 关键字不能换中文；缩进也影响执行 |
| async / await | 异步函数与等待异步结果 | 不能随意删掉 await，否则可能拿到尚未完成的操作 |
| class / async with / yield | 定义类、管理异步资源、向框架交出资源 | async with 结束时关闭异步会话；yield 后续清理由框架安排 |
| FastAPI / APIRouter / Depends | FastAPI 提供的工具名 | 从库导入时按库名称拼写 |
| @router.get / post / patch / put | 登记不同 HTTP 操作 | 方法应与前端实际请求方法一致 |
| prefix / response_model / status_code | FastAPI 识别的参数名 | 参数名固定，参数值由接口设计决定 |
| BaseModel / Field / ConfigDict | Pydantic 的数据检查工具 | 自己的数据模型类名可改 |
| DeclarativeBase / Mapped / mapped_column | SQLAlchemy 声明表结构的工具 | 用它们描述列类型、外键等 |
| __tablename__ / __table_args__ | SQLAlchemy 识别的特殊属性 | 属性名按库要求，表名与约束内容属于项目设计 |
| select / where / order_by / limit | 构造数据库查询 | 方法名固定，查哪张表、筛什么条件可以设计 |
| session.commit() | 提交这次数据库修改 | 不要为了让页面显示成功而跳过真正提交 |
| createApp / ref / computed / onMounted | Vue 提供的函数 | 使用时要 import；自己起的变量名可改 |
| ref 的 .value | 在脚本中读写响应式值 | 模板中通常直接使用变量，不必写 .value |
| v-model / v-if / v-for | 绑定输入、条件显示、循环显示 | 指令名固定，绑定的变量和条件由你设计 |
| @click / @submit.prevent | 处理点击、处理提交并阻止页面默认刷新 | 事件名按浏览器/组件要求 |
| :disabled / :loading | 让组件参数跟随变量变化 | 冒号表示后面是表达式，不是固定文字 |
| <script setup lang="ts"> | Vue 单文件组件里的脚本约定 | TypeScript 写在这里 |
| RouterLink / RouterView | 页面链接与当前页面的显示位置 | 按 Vue Router 组件约定使用 |
| defineStore | Pinia 声明共享状态 | 'auth' 是本项目给 store 起的标识 |
| z.object / z.enum / schema.parse | Zod 检查收到的 JSON | 检查完成后，页面按约定使用数据 |

这些写法仍有其他正确用法。对新手来说，先保持当前写法跑通，再学习替代方式。

## 第二类：命名可以改，但引用要一起改

| 例子 | 哪部分是自己起的 | 改的时候同步哪里 |
|---|---|---|
| app = FastAPI() | app | 启动命令冒号后的对象名 |
| def create_ticket(...) | create_ticket | Python 直接调用它的地方；路由字符串不会自动变 |
| class TicketCreate(BaseModel) | TicketCreate | import 和使用该类型的参数 |
| const isChecking = ref(false) | isChecking | 当前脚本、模板里的同名引用 |
| function checkHealth() | checkHealth | onMounted、@click 等调用处 |
| src/api/health.ts | health.ts | import 路径 |
| App.vue | App.vue | main.ts 中的 import；文件名大小写要一致 |
| 'auth' | store 标识 | 同一个项目里保持唯一并核对相关引用 |

`isChecking`、`customer_email` 这些名字用来表达“是什么”，不要为了缩短写成看不懂的缩写。
文件和函数不是拆得越多越好；当前 service.py 放的是已经被多个路由实际使用的业务操作。

## 第三类：项目约定可以设计，但有联动

| 约定 | 当前值/写法 | 修改影响 |
|---|---|---|
| 后端地址 | 127.0.0.1:8000 | 后端启动端口与 Vite proxy target 一起改 |
| 前端端口 | 5173 | 浏览器访问地址一起改；strictPort 避免占用时悄悄换端口 |
| 接口前缀 | /api | 后端 prefix、前端 request、Vite 代理匹配规则一起改 |
| 健康接口结果 | {"status":"ok"} | 后端返回值与前端 schema/边界检查一起改 |
| 登录请求字段 | username、password | 表单提交对象与后端请求 schema 一起改 |
| 工单字段名 | title、description、priority 等 | 后端请求/响应、模型、前端 schema、表单和页面一起改 |
| 工单状态代码 | pending/processing/resolved/closed | 状态校验、数据库约束、前端显示映射、按钮规则和测试一起改 |
| 角色代码 | admin/staff | 后端权限、数据库约束与前端导航一起改 |
| 数据表名 | users、tickets 等 | 模型、外键与数据库迁移一起改 |
| 优先级 | P1～P4 | 后端枚举、数据库约束、前端选项与业务规则一起改 |
| 字段长度 | 标题 200、正文 10000 等 | 前端输入限制、后端校验；表列长度变化还需迁移 |
| 登录有效期 | 8 小时（480 分钟） | backend/.env 的 ACCESS_TOKEN_MINUTES；值域检查也要保持业务一致 |
| 请求等待时间 | 健康 5 秒、业务 10 秒、连接数据库 5 秒 | 当前示例的参数选择，按实际需要调整 |
| 每页条数 | 默认 20，最多 100 | 后端分页规则、前端 pagination 的 page-size 与测试一起改 |

“HTTP 401 表示没有有效登录”“403 表示无权操作”“404 表示不存在”
“409 表示状态或唯一性冲突”“422 表示输入不符合要求”，是本例沿用的 HTTP 语义。
不要为了让前端分支少一些而把这些错误全部改成 HTTP 200。

## 第四类：显示内容通常可直接改

你可以先尝试这些修改来熟悉工程：

- 页面标题“售后工单智能辅助系统”。
- 按钮文字“重新检查”“保存工单”。
- 表单标签、输入提示、空列表提示。
- CSS 颜色、间距、宽度和圆角。

例如 `label="客户邮箱"` 是页面显示文案，通常可以直接改。
`v-model="form.customer_email"` 是绑定到数据字段；它不是随便换一句中文就能改的文案。

页面暂时没有数据是正常状态；请求失败则必须显示错误，不能用“暂无数据”冒充加载成功。

## 第五类：本地配置必须由自己的环境提供

- .env 中数据库密码需要与自己创建的 PostgreSQL 用户匹配。
- JWT_SECRET 由 configure.py 随机生成，只用于后端签名。
- 登录密码由管理员初始化或创建客服时设置。
- 端口、数据库主机和库名要与实际服务一致。

configure.py 中的本机地址和 after_sales 名称属于本教程选定的环境，
不是框架固定要求。如果你换了数据库用户或地址，修改脚本配置和 .env，
并用 Alembic 迁移确认连接。

示例配置文件可以给别人看；真实 .env、.env.test、密码与令牌不要放进源代码或日志。
日志不需要打印完整 Authorization 请求头来排查普通业务错误。

## 这套代码为什么保留这些检查

| 检查/处理 | 当前依据 | 放在哪层 |
|---|---|---|
| 请求字段长度、枚举、邮箱、必填 | 页面确实允许用户输入，接口也可被直接调用 | 后端 Pydantic 请求边界 |
| 登录签名、有效期、账号启用状态 | 每个业务接口必须知道是谁在操作 | 后端认证依赖 |
| 管理员权限 | 客服不能创建账号或修改基础配置 | 后端权限依赖 |
| 产品与模块匹配 | 创建/编辑工单会从配置中选择这些字段 | 工单业务操作 |
| 停用项保留历史但禁止新选择 | 已确认的历史数据规则 | 工单业务操作与数据库外键 |
| 新负责人是否启用 | 页面允许重新分配工单 | 工单编辑业务操作 |
| 状态顺序与解决方案 | 工单生命周期的明确要求 | 对应业务路由与数据库约束 |
| 唯一名称冲突 | 用户名、产品名、分类名与产品内模块名有唯一约束 | 捕获 PostgreSQL UniqueViolation 并返回 409 |
| JSON 响应格式 | 浏览器确实从多个 HTTP 接口接收数据 | 前端 API 边界 |
| 页面 catch Error | 当前页面可以把请求错误显示给操作人 | 页面层，非 Error 异常继续抛出 |
| 超时 | 连通性和业务请求不应无限等待 | 数据库连接与 HTTP 请求 |
| AsyncSession 关闭 | 每次请求实际申请了数据库会话 | async with 管理会话 |
| 工单行锁 | 两名客服实际可能同时处理同一工单 | 写入工单时 |

没有自动重试。创建工单这类写操作不能因为前端没收到响应就直接重复发送；
当前页面显示错误，让操作人先核实结果。

唯一性处理只识别当前采用的 PostgreSQL 错误，其他数据库异常继续暴露给服务端。
不做跨数据库兼容，不把上游失败改成默认成功，也不在页面重复校验已经通过 API schema 的响应。

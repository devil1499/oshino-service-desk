# 前三部分代码与小白跟写教程

这是一套按你的售后工单项目整理的参考代码。先跟写一个阶段、运行验收，再进入下一阶段。

## 从哪里开始

1. 先读 [学习顺序与术语](00-学习顺序与术语.md)。
2. 按 [第一部分：前后端连通](01-前后端连通.md) 完成健康检查。
3. 按 [第二部分：数据库、登录与基础配置](02-数据库登录与配置.md) 完成管理员和客服账号。
4. 按 [第三部分：工单管理闭环](03-工单管理闭环.md) 完成创建、处理、解决与关闭。
5. 对照 [固定写法与可修改项](04-固定写法与可修改项.md) 再尝试改代码。
6. 不清楚某个文件时，查 [逐文件代码与讲解](05-逐文件代码与讲解.md)。

逐文件讲解使用下面的阶段名称区分源码版本；这些不是本仓库内的可运行目录：

| 阶段标记 | 内容 | 需要数据库吗 |
|---|---|---|
| `01-connectivity` | 健康接口、Vue 页面、开发代理 | 不需要 |
| `02-foundation` | 第二部分完整前后端，包含第一部分健康检查 | 需要 |
| `03-tickets` | 第三部分完整前后端，包含前两部分功能 | 需要 |

仓库中的参考源码写在教程代码块内，正式代码由你写入根目录的 backend/frontend。第二、三部分的参考代码共享同一条数据库迁移历史；已有正式工程的迁移衔接先读 [异步数据库与跟写约定](../../02-项目说明/异步数据库与跟写约定.md)。
从第二部分进入第三部分时，保留原数据库和本地 `.env`，增加代码并运行 `python -m alembic upgrade head`。
已经创建管理员后无需重复初始化。

## 跟写的目标目录

教程中的命令统一以你手写到 `E:\oshino` 为准：

```text
E:\oshino\backend\...   ← 对照该阶段 backend 下的同名文件
E:\oshino\frontend\...  ← 对照该阶段 frontend 下的同名文件
```

例如：逐文件讲解标记为 `03-tickets/backend/app/modules/tickets/router.py` 的代码，
对应你要写的文件是 `E:\oshino\backend\app\modules\tickets\router.py`。

所有命令都在 WSL Ubuntu 中执行。Python 虚拟环境使用现有的 `/mnt/e/xiangmu/.venv`；前端依赖由正式工程 `frontend/package.json` 与匹配的锁文件管理。

## 这三部分采用的业务规则

- 登录用户分为管理员与客服。管理员维护客服账号、产品、模块、分类。
- 所有启用的登录用户可以查看、处理内部工单；负责人表示工作分配。
- 新工单负责人是创建人，状态是待处理。优先级由创建人选择。
- 状态按“待处理 → 处理中 → 已解决 → 已关闭”推进。
- 标记已解决必须填写解决方案。关闭时，客服确认已经在系统外完成客户回复。
- 关闭后的工单只允许查看，保留处理记录。
- 停用配置保留历史关联，不能用于新的选择。
- 登录令牌保存在当前标签页的 sessionStorage，刷新后核验身份并恢复；有效期为 8 小时，退出登录清除令牌。
- CSV 批量导入在第四部分，检索与 AI 在第五至七部分；OCR 和系统内邮件发送不在当前八部分学习版范围。

## 跟写时的依赖安装

在 WSL 的 `/mnt/e/oshino/frontend` 目录操作：如果自己填写了 `package.json`、还没有 `package-lock.json`，先运行 `npm install` 生成锁文件。若已有配套的依赖清单和锁文件，运行 `npm ci`。锁文件不需要手抄，也不要把旧阶段的锁文件与新依赖清单混用。之后运行 `npm run typecheck`、`npm run build`，通过后再 `npm run dev`。

按阶段对照新增和修改的代码，不把不同阶段的同名文件随意覆盖。深色三栏工作台在第八部分后的“工作台界面改版”中；前面的简洁页面用于逐步学习。

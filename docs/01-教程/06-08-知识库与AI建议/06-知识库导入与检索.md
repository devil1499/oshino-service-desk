# 第六部分：知识库导入与检索

目标：把产品说明和操作规范变成可检索的知识，打开工单时能找到相关段落并查看文档出处。

通用方法另见 [知识库切分、清洗与向量化速查](19-知识库切分清洗与向量化速查.md)：包括不局限于本项目的切分方案、PDF/OCR 选择、数据清洗、存储格式与质量验收。这里的 500 字符、80 字符重叠是便于学习的起点，不是通用最优参数。

## 先理解流程

上传或录入正文 → 草稿 → 管理员校对 → 发布并分块 → 停后端建索引 → 启动后端检索。

PostgreSQL 存完整文档和正式分块；Milvus 是可重建的检索副本。“发布”先把确认后的文字存好，“建索引”再调用模型把分块变成向量，两步各有明确结果。

本阶段支持 UTF-8 的 `.md`、`.txt`，每个文件最多256 KiB，正文1—100000字符。Markdown 按纯文本显示，不执行其中的HTML。跟写时把样例保存在 `data/raw/knowledge`，并明确标注模拟资料；仓库中的占位目录不表示已有可导入样例。

## 跟写顺序

1. `backend/app/models.py` 的 KnowledgeDocument 和 KnowledgeChunk；新增迁移 `06_knowledge.py`。
2. `modules/knowledge/text.py`：500字符切块，80字符重叠；schemas.py 定义输入输出。
3. `modules/knowledge/router.py`：录入、上传、保存草稿、发布、停用。
4. `integrations/hybrid_index.py`：把案例和知识共同使用的索引操作放一起；case_index.py 保留案例接口，knowledge_index.py 使用知识集合。
5. `app/rebuild_knowledge.py`：只重建知识集合，保留案例集合。
6. `modules/knowledge/search.py` 和 `main.py`：接通工单查询知识的接口。
7. 前端 `api/knowledge.ts` → KnowledgeView.vue → KnowledgeEditor.vue → KnowledgeMatches.vue → router/index.ts、App.vue、TicketDetailView.vue。

变化和对应代码见 [逐文件讲解](09-逐文件代码与讲解.md)。已有文件按参考版本对照修改，不覆盖自己的无关改动。接入当前后端时遵循 [异步数据库与跟写约定](../../02-项目说明/异步数据库与跟写约定.md)。

## 当前 Docker 工程

本机已实现第六部分，继续使用 Windows Ollama 的 `qwen3-embedding:0.6b`、1024 维。知识页已连接 PostgreSQL，保持当前浅色界面。

在 WSL 项目根目录启动和升级：

```bash
cd /mnt/e/oshino
docker compose --env-file .env.docker up -d --build --wait
```

当前已发布 4 份模拟文档并建立 4 个知识分块。打开 `/knowledge` 可搜索、阅读和管理；打开工单详情点击“检索知识文档”。资料仅用于毕业设计演示。

以后导入或修改文档并发布后，按以下顺序重建知识索引：

```bash
docker compose --env-file .env.docker stop backend
docker compose --env-file .env.docker run --rm --no-deps backend python -m app.rebuild_knowledge --replace
docker compose --env-file .env.docker up -d --wait backend
```

即使重建失败也要重新启动后端。此命令保留 PostgreSQL 工单及原案例集合。本机验证与验收步骤见[第六部分实施与验收](../../03-检查记录/2026-10-31-第六部分实施与验收.md)。

## 直接在 WSL 运行时的安装与数据库升级

以下为独立运行后端的参考步骤，不与 Docker 同时占用端口；还需配置该 WSL 环境实际可达的模型地址。前提是你已经跟写到正式工程，并完成前五部分。

```bash
cd /mnt/e/oshino
source /mnt/e/oshino/.venv/bin/activate
python -m pip install -r backend/requirements-dev.txt
cd backend
python -m alembic upgrade head
```

这次复用第五部分依赖，不新增Python包。两个新表分别存文档和分块，原工单不变。前端仍使用现有依赖；首次安装且已有匹配锁文件时，在 `/mnt/e/oshino/frontend` 运行 `npm ci`。

## 自己操作一次

1. 在 backend 中按原命令启动：`python -m uvicorn app.main:app --reload --port 8000`。
2. 另开 WSL 终端，进入 `/mnt/e/oshino/frontend`，运行 `npm run dev`。
3. 管理员登录后进入“知识库”，点击“录入或上传知识文档”。
4. 填标题，选择启用的产品、所属模块和分类，上传样例或输入正文，保存草稿。
5. 阅读正文，修改后先保存，再点击“发布已保存正文”。看到 published 和分块数量才算发布成功。
6. 停止后端，在 backend 运行：

```bash
python -m app.rebuild_knowledge
```

已有知识索引时用：

```bash
python -m app.rebuild_knowledge --replace
```

7. 建索引成功后重新启动后端。打开一个同产品模块工单，点击“检索知识文档”，应看到片段、文档名、分块编号和出处链接。

案例索引与知识索引使用同一个 `MILVUS_DB_PATH`，但集合和就绪文件不同。升级后沿用第五部分模型、地址、维度时，既有案例索引仍可使用。若换模型或维度，应分别重建两类索引。

Milvus Lite 继续按单后端进程使用。重建期间停止后端，不同时运行多个重建任务。

## 编辑与停用

列表搜索覆盖服务端标题和正文，管理员还可筛选文档状态。界面有未保存修改时会禁用发布、停用，先保存再操作。

编辑保存会让文档回到 draft，并移除旧正式分块；要重新发布、重建知识索引。停用后，查询会依据 PostgreSQL 当前状态丢弃旧命中；不会等到重建才生效。重新发布会产生新分块，需要重建才能找得到。

管理员能看到草稿、已发布、停用资料；客服只能列表和阅读已发布资料。权限由后端控制，不能靠前端隐藏按钮代替。

查询先同产品模块，不足五块再查同分类；最多五个片段，同一文档可以命中不同分块。score 是排序值，不是准确率。stale_count 是本次遇到的失效分块数，不是全库统计。

## 固定写法和可改内容

| 代码 | 意思 | 修改规则 |
|---|---|---|
| `UploadFile`、`Form` | FastAPI 接收文件与表单 | 接口名是框架规定；表单字段要与前端一致 |
| `500`、`420` | 每块500、下一块向前走420，留下80重叠 | 是项目参数，改后重新发布文档和重建索引 |
| `draft/published/disabled` | 草稿/已发布/停用 | 是状态契约，前端、数据库约束和查询须一起改 |
| `knowledge_chunks` | Milvus集合名 | 是项目命名，改后同步重建与查询 |
| `load_collection` | 新进程查询前加载集合 | 是当前Milvus API要求，保留 |

第六部分验收：上传后可编辑、发布后有分块、检索有出处；草稿不参与检索、停用立即被过滤；错误不能显示成成功空结果。

依赖安装提示：`npm ci` 需要当前依赖对应的 `package-lock.json`。跟写时还没有锁文件，先在 `frontend` 运行 `npm install`；已有匹配锁文件时运行 `npm ci`。

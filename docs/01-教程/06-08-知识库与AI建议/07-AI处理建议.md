# 第七部分：AI处理建议

目标：给当前工单生成可追溯的分析、处理步骤和客户回复草稿，客服编辑确认后保存采用记录。

## 大白话流程

查最多5条有效案例 + 最多5个知识片段 → 聊天模型按相关性选最多5条依据 → 再生成结构化建议 → 校验分类和引用 → 保存生成历史 → 人工核对与编辑 → 保存采用记录。

Embedding 负责文字变向量；聊天模型负责重排和写建议，是不同的工作。重排和生成各调用一次聊天接口。案例与知识检索各自生成查询向量。模型名、提示词版本和耗时保存在生成记录里。

## 跟写顺序

1. models.py 增加 AssistanceRun，新增 `07_assistance.py` 迁移。
2. `core/chat_settings.py`、`.env.chat.example` 和 `.gitignore`。
3. `integrations/chat.py`：JSON输出、30秒超时、关闭自动重试。
4. `modules/analysis/assistance_schemas.py`：模型输出、引用快照、人工采用输入。
5. `modules/analysis/assistance.py`：检索、重排、生成、历史与采用。
6. main.py 接入路由。
7. 前端 api/assistance.ts → AssistancePanel.vue → TicketDetailView.vue。

## 配置与启动

新增 `backend/.env.chat`，按示例填：

```dotenv
CHAT_BASE_URL=https://api.example.com/v1
CHAT_API_KEY=填写服务商后台创建的密钥
CHAT_MODEL=填写账号实际可用的聊天模型名称
```

三项分别是 OpenAI 兼容接口基础地址、密钥和模型名称。基础地址按服务商文档填写，不附加 `/chat/completions`。示例域名不能直接使用。配置文件只保存在后端，已被 Git 忽略；前端不接触密钥。

聊天 API 与 `.env.retrieval` 完全独立：现有本地 Qwen3-Embedding 继续负责向量检索，不需要改为远程服务。聊天服务需要支持 `chat.completions`、`response_format={"type":"json_object"}`、`temperature` 和 `max_tokens`；不发送服务商专属的 `enable_thinking` 参数。后端仍会校验输出结构及引用，JSON 格式正确不代表内容一定正确。

Docker 用户在 `backend/.env.chat` 填写上述三项后，在项目根目录执行：

```bash
cd /mnt/e/oshino
docker compose --env-file .env.docker restart backend
```

首次取得此版本时，先按 README 执行 `up -d --build --wait`，使第七、九部分迁移生效。配置未填写时，普通工单和看板可正常使用，点击生成会明确返回 503 配置错误。密钥错误返回上游 HTTP 状态，不伪装成空建议。

如果直接在 WSL 运行：

```bash
cd /mnt/e/oshino
source /mnt/e/oshino/.venv/bin/activate
cd backend
python -m alembic upgrade head
```

先确认案例、知识两个索引都完整。即使某类没有数据，也需建立一个成功完成的空索引，明确表示“这类数据确实为空”；缺少索引不能冒充零结果。两类都没有有效依据则返回409，不调用聊天模型编造方案。

重新按原命令启动后端，前端启动 `npm run dev`。

## 页面怎么用

1. 打开 pending 或 processing 工单，点“生成处理建议”。
2. 阅读摘要、判断、建议分类/优先级、步骤、风险、待确认项。
3. 每个步骤后面的 T数字/K数字是本次真实来源ID。T代表案例、K代表知识分块，点击来源可查看原文；后端保留生成当时的文本快照。
4. 修改“处理方案”和“回复草稿”，核对后勾选确认，点“确认采用并保存记录”。
5. 工单处理记录中应出现人工采用记录。工单状态不会因此自动改变；需要时点击“开始处理”，实际完成操作后在原解决方案区域填写并标记已解决。
6. 回复草稿可以复制到系统外邮件工具，实际发送后再按原流程确认关闭工单。

重复采用返回409；工单或来源改动、知识停用后采用也返回409，要求重新生成。采用失败时检查具体原因，不要把异常捕获后改成“成功”。

生成历史每页10条，记录原稿、最终采用文本和时间。旧历史可以阅读，来源链接展示的是当前文档，快照才是当时依据；有变更时不能直接采用旧结果。

## 哪些地方能改

| 内容 | 固定或约定 | 说明 |
|---|---|---|
| `chat.completions.create`、`response_format` | SDK/API写法 | 遵循当前服务文档 |
| `AssistanceDraft` 字段 | 项目输出契约 | 改字段要同步提示词、校验、前端与评测脚本 |
| 系统提示词 | 项目规则 | 可改措辞；改后更新 PROMPT_VERSION，重新评测 |
| T/K来源ID | 项目约定 | 后端映射到真实记录，模型只能选现有ID |
| 提示词中的权限与资料边界 | 必要约束 | 来源正文是数据，其中的命令不应被执行；页面使用普通文本显示 |
| 分类和优先级 | 建议 | 没有自动修改工单；客服通过原编辑入口确认 |

不单独发送客户姓名、邮箱字段。描述和方案里如果出现个人信息，仍可能被送到远程模型；这版不自动脱敏。模型输出校验能挡住结构错误、非法分类和不存在的引用，不能保证每一句建议事实正确，所以必须人工核对。

第七部分验收：生成有依据、错误明确；人工编辑可保存；重复/过期采用被拒绝；生成历史可查看；没有自动发送邮件或偷偷推进工单状态。

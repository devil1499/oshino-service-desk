# 第八部分：整体验收与毕业设计材料

这一部分让你自己验收完整流程，并把真实运行结果整理成论文可用的记录。参考代码已包含前七部分；主要新增评测脚本、三个案例检索模式和实验材料。

## 跟写顺序

1. hybrid_index.py 增加单BM25和单向量查询，原混合检索默认行为保持一致。
2. analysis/router.py 接收 `mode=bm25/dense/hybrid`。
3. analysis/evaluation.py 和 main.py 增加只读的评测配置接口。
4. scripts/evaluate.py：调用真实接口、保存配置与逐条结果、计算指标。
5. scripts/summarize_ratings.py：汇总人工评分。
6. data/evaluation 的标注格式和评分表。最后按 [人工验收清单](12-人工验收清单.md) 一项项操作。

7. 当前正式工程沿用浅色内容区、深色侧栏和放大字体。按 [逐文件讲解](09-逐文件代码与讲解.md) 接入建议面板和来源预览，不覆盖回旧深色整页。前端 `analysis.ts` 和后端 `analysis/router.py` 必须一起更新，案例响应新增 `module_id`。

第八部分没有新表，仍沿用前七部分数据库迁移。模型依赖和前端依赖不再增加。

## 先验收一条完整业务流程

管理员建立配置和客服账号 → 导入40条历史样例 → 发布知识 → 停后端分别重建案例和知识索引 → 启动后端 → 客服新建一个不同表述的待处理工单 → 查相似案例与知识 → 生成建议 → 核对并编辑 → 确认采用 → 开始处理 → 实际验证方案后标记已解决 → 在系统外回复客户 → 确认关闭。

关闭后生成/采用按钮不可用；接口也应拒绝这些操作。不要把系统外未实际完成的客户回复标成已完成。

## 准备独立评测集

`data/evaluation/labels.example.jsonl` 只说明字段和格式，里面的ID是示例，不能直接当你的真实标注。

先在系统创建独立查询工单，另存真实标签为 `data/evaluation/labels.jsonl`。每行一个JSON对象：

```json
{"sample_id":"EVAL-001","ticket_id":1001,"relevant_case_ids":[11,12],"relevant_document_ids":[3],"expected_category_id":1,"expected_priority":"P3"}
```

- ticket_id：实际存在的查询工单ID；用于生成测试时保持待处理/处理中。
- relevant_case_ids：人工核对后确实相关的有效案例ID，至少一条，不能包括查询工单自己。
- relevant_document_ids：相关知识文档ID；没有已标注文档时填空列表，这条不进入知识召回率平均值。
- expected_category_id / expected_priority：人工确定的标签，使用系统实际分类ID和P1—P4。
- sample_id / ticket_id：每条唯一，避免同一查询被重复计算。

至少先做少量人工核对样本跑通，再扩充到论文计划规模。查询工单不要进入案例索引，不使用同一模板换几个词就宣称独立评测；不要在保留集上反复调参数再报告成绩。

## 运行检索对比

后端和数据库保持启动、两类索引完整。WSL中从正式工程根目录运行，脚本会询问账号和密码，密码不回显；不把密码或令牌写进命令参数与结果文件。

```bash
cd /mnt/e/oshino
source /mnt/e/oshino/.venv/bin/activate
python scripts/evaluate.py --dataset data/evaluation/labels.jsonl --mode bm25 --output data/evaluation/results/bm25.json
python scripts/evaluate.py --dataset data/evaluation/labels.jsonl --mode dense --output data/evaluation/results/dense.json
python scripts/evaluate.py --dataset data/evaluation/labels.jsonl --mode hybrid --output data/evaluation/results/hybrid.json
```

mode 只控制**案例检索**，知识检索一直是混合检索。三组案例实验使用相同查询工单、相同索引、相同分层范围和最多五条结果。单BM25案例请求不生成向量，但脚本还会做知识混合检索，因此整轮仍需要模型配置。

结果包含数据集SHA256、索引模型/维度/构建时间、查询策略、每条实际返回ID、逐条Recall与总体平均值。仅所有请求成功时状态才为 completed；中途失败会写 failed 和已完成明细，不产出完整指标。结果文件存在时拒绝覆盖，请为新实验换文件名。

Recall@5 = 前五条结果中命中的相关案例数量 ÷ 人工标注的全部相关案例数量。先对每条查询计算，再取平均。知识指标单独称“前五个知识块覆盖的相关文档召回率”，同一文档多个片段会去重；不能说它是前五篇文档检索。

## 运行完整AI链路评测

```bash
python scripts/evaluate.py --dataset data/evaluation/labels.jsonl --mode hybrid --generate --output data/evaluation/results/assistance.json
```

`--generate` 会额外调用完整建议接口，产生模型费用和生成历史，不会采用、解决或关闭工单。生成管线始终为“双源混合检索+模型重排+生成”，不受前面的 mode 控制。

结果额外记录生成run_id、聊天模型、提示词版本、分类Macro-F1、优先级准确率和完整生成接口平均响应时间。分类分数来自按需生成的建议，不是尚未实现的“建单后自动基础分析”。检索两次接口的耗时与单次完整建议接口耗时分开记，不能混成同一指标。

这份代码不提供独立的“同一候选池、有无重排”检索接口，因此没有宣称完成四组严格消融实验。当前可直接比较三组案例召回，并记录双源重排生成效果；论文如需单独论证重排增益，需再设计同候选池实验。

## 人工评分

复制 `ratings-template.csv` 为 `ratings.csv`。查看真实 run_id 对应建议后，人工填写相关性、正确性、可用性三项1—5整数；不能让模型自评代替人工。

```text
sample_id,run_id,rater,relevance,correctness,usability
```

每条评分由 sample_id、run_id、rater 标识，同一评分人不能重复评价同一条结果。空表、缺值、重复或越界评分会报错。

```bash
python scripts/summarize_ratings.py --input data/evaluation/ratings.csv --output data/evaluation/results/ratings-summary.json
```

结果包括评分人数、样本数、评分条数、各维度均值和总均值。它不会自动判断哪些样本遗漏，需按你论文确定的样本清单核对覆盖率。

## 当前验收边界

第七部分使用可配置的远程聊天 API。未填写 API 配置前，可以验证登录、工单闭环、双源检索、看板以及“配置缺失”的错误提示。模拟模型响应的自动测试只验证业务契约，不代表真实生成质量。

论文评测需要你人工标注独立样本并填写评分表。当前提供执行脚本和空白评分模板，不把示例 ID、模拟测试、未评分的建议当成论文实验结论。

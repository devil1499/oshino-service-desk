# 第九部分：统计看板

沿用当前浅色内容区和深色侧栏。本部分源码标记为 `09-dashboard`，变化文件在 [逐文件代码与讲解](13-逐文件代码与讲解.md) 的代码块中对照；这不是仓库中另一个可运行的工程目录。

## 做完能看到什么

左侧“工作概览”显示工单总数、状态分布、优先级分布、平均解决时长及有效样本数。按产品筛选后，所有统计使用相同范围。数据来自 PostgreSQL 查询，页面没有写死演示数字。

## 先理解统计口径

统计范围是当前系统全部工单，管理员和售后客服都能访问，与已有工单列表的可见范围相同。已关闭工单也计入已知解决时长。首次解决时间减创建时间得到小时数；关闭时间、最近更新时间都不能代替解决时间。

历史导入工单没有可靠解决时刻时，`resolved_at` 为 null，只计入工单数量，不参与时长平均值。没有时长样本时，接口返回 null，页面显示“暂无样本”。状态数量为零时显示 0，这是计数本身的业务含义。

## 跟写顺序

1. 在 `backend/app/models.py` 的 Ticket 中增加 `resolved_at`。它保存实际解决时间，`DateTime(timezone=True)` 是 SQLAlchemy 的时区日期类型写法。
2. 增加 `backend/migrations/versions/09_resolution_time.py`。迁移只从原有“保存解决方案：处理中 → 已解决”记录回填时间；没有该记录就保留空值。
3. 在 `backend/app/modules/tickets/router.py` 的解决接口写入当前时间。前端不能自己决定数据库中的解决时刻。
4. 新增 `backend/app/modules/dashboard/router.py` 并在 `app/main.py` 注册。`@router.get`、`response_model`、`select` 是框架接口；路径 `/api/dashboard` 是本项目约定，改时要同步前端。
5. 新增前端 `api/dashboard.ts`、`views/DashboardView.vue`，在路由和侧栏添加入口，补充 CSS。数字来自接口，标题、颜色和间距可以改。
6. 补数据库迁移，执行类型检查、构建，再打开页面验收。

## 在 WSL 验证

跟写到正式工程后，使用已有 Linux 虚拟环境。在 backend 目录运行：

```bash
cd /mnt/e/oshino
source /mnt/e/oshino/.venv/bin/activate
cd backend
python -m alembic upgrade head
python -m uvicorn app.main:app --reload --port 8000
```

前端另开 WSL 终端：

```bash
cd /mnt/e/oshino/frontend
npm run typecheck
npm run build
npm run dev
```

上面的命令都在正式工程运行，不需要切换到旧 `outputs`。依赖清单与锁文件保持匹配；新增依赖后按配置说明更新，不复制旧阶段锁文件覆盖当前文件。

## 自己验收

- 未登录直接请求接口应返回 401。
- 一个新产品没有工单时，总数和分布为零，平均时长显示“暂无样本”。
- 创建工单、开始处理、解决、关闭后刷新统计，数量随数据库变化。
- 数据库里有可靠解决时间的工单才增加“有效时长样本”。
- 切换产品后，所有数字一起变化；接口失败时显示错误，不把旧统计当新结果展示。

本部分新增测试在 `backend/tests/test_dashboard.py`。测试只使用名称以 `_test` 结尾的专用 PostgreSQL 数据库，配置方式见 [配置与运行](14-配置与运行.md)。

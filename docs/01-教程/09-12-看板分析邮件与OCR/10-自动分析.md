# 第十部分：自动分析

累计工程为 `10-analysis`，先完成第九部分。本部分把“基础分析”接到工单创建后：先保存工单，再在后台生成摘要、问题分类及优先级建议。历史 CSV 导入不会逐条调用模型，避免导入时产生大量外部请求。

## 数据怎样流动

创建工单 → 同一个数据库事务保存分析任务 → 返回工单 → 后台读取快照并调用聊天模型 → 保存完成或失败状态 → 详情页读取状态 → 客服核实并确认采用。

后台采用独立数据库会话，不能继续使用请求结束后的会话。分析建议保存在 `basic_analyses` 表中，工单原分类和优先级要到人工确认后才修改。该分析不依赖 Milvus 索引；后续查案例、查知识和生成处理建议仍使用原功能。

## 跟写顺序

1. 在 `models.py` 添加 BasicAnalysis，添加 `10_basic_analysis.py` 迁移。
2. 添加 `modules/analysis/basic.py`，读懂结果结构、工单内容指纹、排队、后台执行、状态读取和确认采用几个入口。
3. 在创建工单接口注入 `BackgroundTasks`。`add_task` 是 FastAPI 的写法，传入的是函数及参数，不是在这里立即调用模型函数。
4. 在 `main.py` 注册接口，并在启动时处理上次进程中断的任务。按教程使用单个 Uvicorn 工作进程；多进程任务队列需要另外设计。
5. 添加前端 `api/basicAnalysis.ts` 和 `BasicAnalysisPanel.vue`，在详情页传入工单和分类映射。只在等待或运行中每 1.5 秒查询一次，离开页面时清理定时器。
6. 执行迁移、类型检查和构建，使用自己的模型配置验收。

`BasicResult` 是返回结构：字段名称和类型要与模型提示、后端校验和前端 Zod 校验一致。摘要与原因的提示语可以调整；`P1`—`P4`、分类 ID 必须遵守当前业务配置。指纹用于发现分析后工单标题、描述或产品模块已变化，不能删除校验来强行采用旧结果。

## 配置与启动

在 backend 的 `.env.chat` 中填写 `CHAT_BASE_URL`、`CHAT_API_KEY`、`CHAT_MODEL`。基础分析只使用聊天配置；`.env.retrieval` 留给向量检索。配置放在本机，完整说明见 [配置与运行](14-配置与运行.md)。不要把真实密钥写进教程或源码。

后台模型失败会保存为 failed，显示实际错误类型；工单仍然存在。缺失配置会明确提示，不生成默认成功结果。手动“重新分析”需要等待上一任务结束。服务重启后，原本等待或运行的任务标记中断，需人工重新触发。

## 自己验收

- 新建工单后，基础分析由等待/运行转为完成，出现摘要、分类和优先级原因。
- 未确认采用前，原工单字段不变；确认后字段与处理记录一起保存。
- 修改问题描述后，旧结果提示过期，后端拒绝采用。
- 模型不可用时显示失败，列表和工单仍能正常使用；修复配置后手动重做。
- 已关闭工单只读，不能重新分析或采用。
- 第九部分及本部分测试在专用测试库运行；真实模型的输出质量、费用与耗时要另外记录。
